# Sonali Paithani

Handwoven Paithani sarees from Yeola, Nashik — storefront, enquiry workflow and
admin dashboard in one deployable app.

Customers do not buy online. They send an **enquiry for one specific saree**; the
studio approves it from the dashboard; the approval — order summary, advance
amount and a UPI payment QR — lands on the customer's WhatsApp as a free
click-to-send message. No payment gateway, no customer accounts.

```
Storefront (React)          API (Express)                    Admin dashboard (React)
  browse collections    →     /api/enquiries       →           approve / reject
  enquire about a saree        stock + audit trail              edit price & advance
  track by reference           WhatsApp + QR links       ←      products, stock,
  Our Legacy, Exhibitions                                       legacy, exhibitions
```

## Stack

| Layer | Choice |
| --- | --- |
| Frontend | Vite 6, React 18, React Router 6, TypeScript (strict), one hand-written stylesheet |
| Backend | Express 4, `pg`, `jsonwebtoken` + `bcryptjs`, `multer`, `qrcode` |
| Database | Postgres (Supabase / Neon). Falls back to in-memory `pg-mem` with **no configuration at all**, then seeds a demo catalogue — perfect for local work |
| Image storage | Supabase Storage, or local `./uploads` in development |
| Payments | UPI link + QR image generated by the server; WhatsApp delivery via `wa.me` click-to-send |
| Deploy | One Node process serves `/api/*` and the built SPA. `Dockerfile` + `render.yaml` included |

## Run it locally

```bash
npm install
npm run dev          # API on :4000, Vite on :3000 (proxies /api and /uploads)
```

Open <http://localhost:3000>. Nothing needs configuring: with no `.env` the API
runs on in-memory Postgres and seeds demo sarees, collections, legacy stories and
exhibitions. Data resets on restart, which is the point.

**Admin dashboard:** <http://localhost:3000/admin> — `admin@sonalipaithani.com` /
`paithani@123` (development defaults only).

Other scripts:

```bash
npm run build        # production bundle → dist/
npm start            # API + built storefront from a single process (:4000)
npm test             # node:test suite (API, QR, WhatsApp)
npm run typecheck    # tsc --noEmit + node --check on the server entry
npm run deploy:check # audit the configuration for production, with fixes
```

Frontend-only changes hot-reload. Server changes are picked up by
`node --watch`.

## Configuration

Copy [`server/.env.example`](server/.env.example) to `server/.env` when you need
to change something. Every value has a working default, so an empty file is
valid. The ones you will actually touch:

| Variable | Why |
| --- | --- |
| `DATABASE_URL` | Real Postgres instead of the in-memory dev database |
| `JWT_SECRET` | Signs admin sessions — any long random string |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | Seeded on the first boot only |
| `STORE_*` | Name, phone, WhatsApp and UPI printed in customer messages |
| `SUPABASE_*` | Photo uploads, so images survive a redeploy |
| `CORS_ORIGIN` / `PUBLIC_BASE_URL` | Your domain, for browser access and payment links |
| `SEED_DEMO_DATA` | Set `false` for a live shop |

## Going live on a domain

See **[DEPLOY.md](DEPLOY.md)** — host setup, the Postgres and storage accounts,
DNS and TLS for your domain, the first-boot checklist, smoke tests and
troubleshooting.

Two things bite everyone once, so they are worth repeating here:

1. **`npm install --include=dev` before building.** Vite and TypeScript are
   devDependencies, and hosts that set `NODE_ENV=production` make npm skip them,
   so `npm run build` fails with `vite: not found`. `render.yaml` and the
   `Dockerfile` already do this.
2. **`ADMIN_PASSWORD` only seeds the first boot.** Changing it later has no
   effect; rotate from *Settings → Dashboard password* in the dashboard.

`npm run deploy:check` checks both, plus a dozen things that quietly lose data.

## How an enquiry flows

1. **Enquire** — the customer opens a saree and taps *Enquire*. The enquiry
   carries that exact piece with quantity, size and colour; the wishlist and
   product page use the same dialog.
2. **Approve** — the dashboard previews the WhatsApp message, sets the final
   total and advance (30% by default), optionally deducts stock, and returns a
   `wa.me` link.
3. **Send** — the studio taps the link; WhatsApp opens with the message already
   written, including a link to the UPI QR image. Marking it sent is recorded
   against the enquiry.
4. **Track** — the customer can check status any time with their reference and
   phone number at `/track`.

Stock is allowed to go negative on approval (flagged *oversold*) rather than
silently clamping to zero, so a made-to-order piece is never mistaken for one
that is physically on the shelf. Manual stock edits still reject negative values.

## Status

Working: catalogue, per-saree enquiries, approval workflow with WhatsApp + UPI
QR, stock with audit trail, admin dashboard (products, stock, enquiries,
collections, settings, Our Legacy, Exhibitions), SEO surface (robots, sitemap,
per-domain canonical/og tags), rate limiting.

Not built on purpose: customer accounts, online payment, shipping integration.
The WhatsApp handoff replaces all three for a made-to-order business.

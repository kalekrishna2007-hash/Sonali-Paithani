# Deploying Sonali Paithani to your own domain

Everything needed to put this store on `https://your-domain.com` — one Node
process serving both the API and the built storefront.

Read §1 and §2, do §3 (or §4 if you prefer Docker), then §5 to attach the domain.
Run `npm run deploy:check` at the end: it re-verifies every claim below against
your actual configuration and tells you exactly what is still unsafe.

```
┌──────────────────────────────────────────────────────────────┐
│  your-domain.com                                             │
│      │  TLS terminated here (platform or Caddy/nginx)         │
│      ▼                                                       │
│  node server/index.js  ── /api/*  → JSON                     │
│                        ── /*      → dist/ (React storefront)  │
│      │                                                       │
│      ├─ Postgres   (enquiries, products, stock, settings)     │
│      └─ Storage    (saree + celebrity + exhibition photos)    │
└──────────────────────────────────────────────────────────────┘
```

---

## 1. What this deploy needs

Two managed services, both free to start. Neither is optional if you want the
shop to survive a restart:

| Piece | Why | Recommended |
| --- | --- | --- |
| **Postgres** | Without `DATABASE_URL` the API runs on an in-memory database (`pg-mem`) and **every product, enquiry, stock count and settings change is erased on restart**. | Supabase or Neon free tier |
| **Object storage** | Without Supabase credentials, uploads are written to `./uploads` on the container filesystem and **disappear on the next deploy**. | Supabase Storage (public bucket) |

You also need somewhere to run Node. Either:

* **A Node host** — Render, Railway, Fly.io, DigitalOcean App Platform. Simplest:
  they build and run the repo, terminate TLS and issue the certificate for your
  domain for you. → §3
* **Docker anywhere** — any VPS, or the Docker option on the hosts above. → §4

Sign-up links and plan names move around; the repo ships [`render.yaml`](render.yaml)
(a Render Blueprint) and a [`Dockerfile`](Dockerfile) so the host-specific part is
already written down.

## 2. Collect these values first

Five minutes in the Supabase dashboard saves an hour of debugging later.

```bash
# 1. A JWT signing key. Anyone holding this can mint an admin session.
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# 2. A dashboard password. 16+ characters, a passphrase is perfect.
#    (Not the ADMIN_PASSWORD from the repo — that one is public.)
```

| Value | Where it comes from |
| --- | --- |
| `DATABASE_URL` | Supabase → Project Settings → **Database** → Connection string → **URI**. Replace `[YOUR-PASSWORD]` with the database password. Append `?sslmode=require`. |
| `SUPABASE_URL` | Supabase → Project Settings → **API** → Project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Same page → **service_role** secret (not the anon key) |
| `STORE_UPI` | Copy the exact VPA from the shop owner's UPI app. A placeholder here means the payment QR pays nobody. |
| `CORS_ORIGIN` | `https://your-domain.com` (add `https://www.your-domain.com` too if you serve both) |
| `PUBLIC_BASE_URL` | `https://your-domain.com` — no trailing slash |

**Create the storage bucket now:** Supabase → **Storage** → New bucket →
name it `product-images` → tick **Public**. Without "public" every uploaded
image URL returns `403`.

## 3. Path A — Render (recommended, ~10 minutes)

1. **Push the repo to GitHub.** Confirm `server/.env` is *not* in the push
   (`.gitignore` covers it — check once with `git status --short`).
2. **Render → New → Blueprint** → pick the repo. Render reads
   [`render.yaml`](render.yaml) and creates the web service.
3. **Fill the `sync: false` variables** (it prompts you):
   `DATABASE_URL`, `ADMIN_PASSWORD`, `CORS_ORIGIN`, `PUBLIC_BASE_URL`,
   `STORE_UPI`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.
   `JWT_SECRET` is generated by Render — leave it.
4. **First deploy.** The build runs
   `npm install --include=dev && npm run build`. The `--include=dev` matters:
   Vite and TypeScript are devDependencies (they are build tools, not runtime
   code), and Render installs with `NODE_ENV=production`, which makes npm skip
   them. Without it the build fails with `vite: not found`. The `Dockerfile`
   does the same thing more explicitly if you prefer Docker.
5. **Confirm it booted**: open `https://<service>.onrender.com/api/health` — you
   want `{"ok":true,...}`. If it 502s, read the logs; a bad `DATABASE_URL` is the
   usual cause and the error message names it.

> Render's own free Postgres expires after 30 days, which is why §2 points at
> Supabase or Neon instead. If you already have a Render Postgres, use its
> **Internal** connection string.

## 4. Path B — Docker (VPS, Fly.io, Railway, DO App Platform)

The image is multi-stage: it builds the bundle with dev dependencies, then ships
a runtime with production dependencies only, as the unprivileged `node` user.

```bash
docker build -t sonali-paithani .
docker run -d --name sonali \
  -p 8080:8080 \
  --env-file server/.env \
  -e PORT=8080 \
  --restart unless-stopped \
  sonali-paithani
```

Put TLS in front. On a bare VPS, [Caddy](https://caddyserver.com) is two lines
and issues the certificate automatically:

```caddyfile
your-domain.com {
    reverse_proxy 127.0.0.1:8080
}
```

nginx works too — remember to forward the client IP, or rate limits will see the
proxy for every visitor:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Point `your-domain.com` at the host (A record → server IP) before starting Caddy
so it can complete the certificate challenge.

**Uploads on a VPS:** either configure Supabase Storage (§1), or keep them on
disk and mount a volume, then acknowledge it:

```bash
docker run -v /srv/sonali-uploads:/app/uploads -e ALLOW_EPHEMERAL_UPLOADS=true ...
```

## 5. Attaching the domain

1. **Add the domain at the host** (Render → Settings → Custom Domains; Fly →
   `fly certs add your-domain.com`; on a VPS it is the proxy config above).
2. **Create the DNS records** at your registrar:

   | Type | Name | Value |
   | --- | --- | --- |
   | `A` (or `ALIAS`/`ANAME` if offered) | `@` | the host's IP, or its apex target |
   | `CNAME` | `www` | the host's target, e.g. `sonali.onrender.com` |

   Apex records can't be `CNAME`s per the DNS spec — that's what `ALIAS`/`ANAME`
   or the host's "apex domain" flow exists for. Cloudflare users get "CNAME
   flattening", which behaves the same way. **Set the Cloudflare proxy to DNS-only
   while the certificate is being issued**, then turn it back on.
3. **Wait for the certificate** (minutes; DNS propagation can take up to an hour).
   `https://your-domain.com/api/health` should answer with `{"ok":true}`.
4. **Update the two domain variables** and redeploy:

   ```
   PUBLIC_BASE_URL=https://your-domain.com
   CORS_ORIGIN=https://your-domain.com,https://www.your-domain.com
   ```

   These are what make the WhatsApp payment-QR link, the canonical tag and the
   `og:image` URL point at your domain instead of a temporary hostname.
5. **Decide on `www`**: either redirect it to the apex in the host's settings, or
   list both in `CORS_ORIGIN` and leave both serving.

While DNS settles you can already preview the real thing locally:

```bash
npm ci --include=dev && npm run build && npm start
# open http://localhost:4000 (the API serves the built storefront too)
```

## 6. Environment reference

Every value has a fallback, so a missing variable boots something — usually the
wrong thing. `npm run deploy:check` catches all of them.

| Variable | Production | Notes |
| --- | --- | --- |
| `DATABASE_URL` | **Required** | Empty → in-memory database, data lost on restart. |
| `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | **Required** | Empty → uploads on ephemeral disk. Supabase → API. |
| `SUPABASE_BUCKET` | `product-images` | Must exist and be **public**. |
| `JWT_SECRET` | **Required**, 32+ chars | `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"` |
| `JWT_EXPIRES_IN` | `12h` | Admin session lifetime. |
| `ADMIN_EMAIL` | `admin@sonalipaithani.com` | Seeds the account on the **first boot only**. |
| `ADMIN_PASSWORD` | 12+ chars, or leave empty | Seeds the first boot only — see §8. |
| `PORT` | injected by the host | Empty/`0` falls back to `4000`. |
| `CORS_ORIGIN` | `https://your-domain.com` | Comma-separate several. Must not still say localhost. |
| `PUBLIC_BASE_URL` | `https://your-domain.com` | No trailing slash. Checkout/QR links and SEO tags. |
| `TRUST_PROXY` | `1` | Number of proxies in front of Node. `1` for Render/Railway/Fly/Cloudflare/nginx; `0` if Node faces the internet directly. Wrong value = shared rate-limit buckets and `http://` links. |
| `SEED_DEMO_DATA` | `false` | `true` stocks the live shop with the demo sarees on the first boot. Set before that boot; the seeder won't run once the catalogue has products. |
| `STORE_*` | set them | Name, phone, WhatsApp, address, UPI — they are printed inside customer WhatsApp messages. |
| `STORE_UPI` | **Set it** | The VPA the payment QR encodes. |
| `DEFAULT_COUNTRY_CODE` | `91` | Prepended to 10-digit customer numbers. |
| `RATE_LIMIT_*` | defaults are sane | Windows are per client IP: 10 sign-ins, 20 enquiries, 60 lookups per 10 minutes. |
| `ALLOW_EPHEMERAL_UPLOADS` | leave unset | Only `true` when `./uploads` really is a mounted volume. |
| `RATE_LIMIT_DISABLED` | leave unset | Debug only. |

## 7. First-boot checklist

Sign in at `https://your-domain.com/admin`, then:

- [ ] `https://your-domain.com/api/health` returns `{"ok":true,...}`
- [ ] The storefront loads over `https://` with no mixed-content warnings
- [ ] `/admin` → **Settings → Dashboard password**: rotate the password (see §8)
- [ ] **Products & stock**: delete or edit the demo sarees, then add real ones
      with real photographs
- [ ] **Settings** → store profile: phone, WhatsApp, address, email, Instagram
- [ ] **Settings** → **UPI ID**: paste the real VPA, then open
      `https://your-domain.com/api/qr/upi.png?pa=<your-vpa>` and scan it with a
      UPI app — confirm the payee name shown is the shop
- [ ] **Settings** → WhatsApp template: send yourself a test approval
- [ ] **Our Legacy** and **Exhibitions**: replace the seeded placeholder entries
      (the demo names and reviews are fictional) with real photos and text
- [ ] Place one real enquiry end-to-end: storefront → dashboard → Approve →
      WhatsApp link opens with the message **and** a tappable payment QR
- [ ] Upload a product photo, then **redeploy** and confirm the image still loads
      (that is the storage check)
- [ ] `https://your-domain.com/robots.txt` and `/sitemap.xml` show your domain
- [ ] Paste the domain into WhatsApp and check the link preview shows the hero
      image

## 8. Rotating the admin password

`ADMIN_PASSWORD` in the environment **only creates the account on the very first
boot**. `ensureAdminUser()` inserts the row when the email is missing and never
touches it again, so changing the variable afterwards does nothing — and if you
booted once with the shipped default, that default is still the live password.

Two ways out:

1. **In the dashboard (normal case):** `/admin` → **Settings → Dashboard
   password** → current + new (12 characters minimum). The hash the login checks
   is updated immediately; nothing to redeploy.
2. **Before the very first boot:** set `ADMIN_PASSWORD` to the strong value in
   the host's environment. This is the cleanest path on a brand-new database.

Sessions already signed in keep working until their token expires
(`JWT_EXPIRES_IN`, 12h), so sign out other devices by shortening that value or
rotating `JWT_SECRET` (which invalidates every session at once).

## 9. Smoke tests

Run against the live domain — these are the same checks a host's health monitor
and a curious crawler perform.

```bash
BASE=https://your-domain.com

curl -s $BASE/api/health                    # {"ok":true,"store":"Sonali Paithani",...}
curl -s $BASE/api/collections | head -c 200 # real collections, not demo ones
curl -s $BASE/robots.txt                    # lists your sitemap URL, disallows /admin
curl -s $BASE/sitemap.xml | head -20        # <loc> entries on your domain
curl -s $BASE/ | grep -o 'og:image[^>]*'    # absolute https URL on your domain
curl -s -o /dev/null -w '%{http_code}\n' $BASE/admin   # 200 (the SPA shell)

# The enquiry path, exactly as a customer hits it:
curl -s -X POST $BASE/api/enquiries \
  -H 'content-type: application/json' \
  -d '{"customer_name":"Smoke Test","phone":"9822055443","items":[{"product_id":"REPLACE_WITH_A_REAL_ID","quantity":1}]}'
```

The last one must return `201` with an `SP-YYYY-NNNN` reference, and the enquiry
must appear in the dashboard. Delete it afterwards.

Rate limiting is working when the 11th rapid sign-in attempt returns `429` with a
`Retry-After` header.

## 10. Day-2 operations

* **Deploys:** push to `main`; the host rebuilds. Render/Railway default to
  auto-deploy on the branch.
* **Backups:** Supabase and Neon take daily snapshots on their free tiers, but
  export `enquiries`, `enquiry_items` and `settings` before any risky migration.
  Products and collections are cheap to recreate; **customer enquiries are not**.
* **Logs:** `docker logs -f sonali` on a VPS, or the host's log viewer. The API
  logs `[api]` for server errors and `[sitemap]` if the catalogue query fails.
* **Scaling out:** rate limits are counted in-process, so N instances allow N×
  the traffic. Fine at this store's size; move the counters to Redis before you
  scale horizontally.
* **Schema changes:** `server/schema.sql` is idempotent and re-applied on every
  boot, so adding `create table if not exists` / `add column if not exists` lines
  is enough — no migration tool.
* **Node version:** `package.json` requires `>=20.11`; the `Dockerfile` pins
  `node:20-alpine` and `render.yaml` pins `20.11.1`.

## 11. Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| Build fails with `vite: not found` | Vite/TypeScript are devDependencies and the host installed with `NODE_ENV=production`. Build with `npm install --include=dev && npm run build` (as `render.yaml` does) or use the `Dockerfile`. |
| 502 / `Application failed to start` | Read the log line above it. Usually a bad `DATABASE_URL` (the message says so) or a missing `pg-mem` because `DATABASE_URL` is empty in a production build. |
| Data resets on every deploy | `DATABASE_URL` is empty — the app is on in-memory Postgres. |
| Uploaded photos 404 after a deploy | No Supabase Storage configured, so images went to container disk. Set the Supabase trio and re-upload. |
| Photos upload but the URL 403s | The Supabase bucket is not **public**. |
| `CMS`/`Not allowed by CORS` in the browser console | `CORS_ORIGIN` still lists localhost, or is missing the `www` hostname. |
| Payment QR link opens `http://` or a temporary hostname | `PUBLIC_BASE_URL` is unset or stale. Set it to the https domain. |
| Every visitor shares one rate-limit bucket, or `req.ip` is the proxy | `TRUST_PROXY` doesn't match the number of proxies. `1` behind one hop, `0` when Node is exposed directly. |
| Site loads but stays on old content | The `dist/` bundle is stale — the build step didn't run. `npm run deploy:check` warns about this locally too. |
| Certificate won't issue | DNS not propagated yet, or Cloudflare's proxy is on during issuance. Switch to DNS-only, wait, retry. |

## 12. Rollback

The storefront is a static bundle plus one process, so rollback is a redeploy:

* **Render/Railway** → Deploys → pick the last good one → *Redeploy*.
* **Docker** → `docker run` the previous image tag
  (`docker build -t sonali-paithani:prev .` before the risky change is a cheap habit).
* **Data** → schema changes are additive and idempotent, so an older image runs
  happily against the newer database. If a deploy wrote bad rows, restore from
  the provider's snapshot instead of hand-editing production.

Nothing here requires downtime beyond the restart, because image uploads live in
object storage and the database is managed externally.
